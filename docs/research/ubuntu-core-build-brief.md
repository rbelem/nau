# Ubuntu Core Image Build Pipeline — Technical Brief

> **Purpose:** Dense reference for building a Rust tool that assembles Ubuntu Core-like images.
> **Sources:** Canonical Ubuntu Core docs (documentation.ubuntu.com/core), ubuntu-image Go source (canonical/ubuntu-image), pc-gadget repo (canonical/pc-gadget/24), snapd seed/seedwriter (snapcore/snapd), Canonical models repo (canonical/models).
> **Date:** August 2026. Covers ubuntu-image 3.x, UC24/UC26.

---

## 1. ubuntu-image Pipeline (Snap Mode)

ubuntu-image is a Go CLI distributed as a snap (`snap install ubuntu-image --classic`). For snap-based images, it takes a **model assertion** file and produces a **disk image** (.img) plus a **seed.manifest**.

### 1.1 State Machine Stages

The internal state machine executes these stages in order (source: `internal/statemachine/snap.go`):

| # | State Function | What It Does |
|---|----------------|--------------|
| 1 | `prepare_image` | Calls `snapd/image.Prepare()` — downloads snaps from the Store (or uses local snaps), builds the seed directory (`system-seed/`), writes assertions. This is the heavy lifting: it resolves the model assertion, fetches gadget/kernel/base/snapd snaps by snap-id+channel, validates assertions, and produces the seed tree. |
| 2 | `load_gadget_yaml` | Reads `meta/gadget.yaml` from the unpacked gadget snap. Parses with `gadget.InfoFromGadgetYaml()`, validates with `gadget.Validate()`. Copies to workdir. |
| 3 | `set_artifact_names` | Sets output filenames (e.g., `pc.img`). |
| 4 | `populate_rootfs_contents` | Moves seed content from `unpack/system-seed/` to rootfs. For UC20+, seed content goes to the rootfs dir (which later becomes `ubuntu-seed`). |
| 5 | `generate_disk_info` | Writes `.disk/info` if `--disk-info` was passed. |
| 6 | `calculate_rootfs_size` | Computes minimum rootfs size from actual content + ext4 metadata overhead (~1.5× + 8MB padding). Respects `--image-size` if larger. Aligns to sector size. |
| 7 | `populate_bootfs_contents` | Uses snapd's `MountedFilesystemWriter` to lay out boot assets (grub.efi, shim.efi, kernel) into partition directories. Handles SecureBoot path remapping. |
| 8 | `populate_prepare_partitions` | For each structure in gadget.yaml: if no filesystem → dd raw content blobs; if filesystem → `mkfs.ext4`/`mkfs.vfat` and populate. Tracks offsets. Grows image if needed. |
| 9 | `make_disk` | Creates the raw disk image file (`diskfs.Create`), generates GPT/MBR partition table (`partition.GeneratePartitionTable`), writes partition data with `dd`-style offset copying, writes `OffsetWrite` values. |
| 10 | `generate_snap_manifest` | Writes `snaps.manifest` listing all snap files with revisions. |

### 1.2 Key Details per Stage

**Stage 1 — prepare_image:**
- Calls `snapd/image.Prepare()` which internally uses `seedwriter.Writer` (snapd's seed writer).
- The seedwriter flow: `SetOptionsSnaps` → `Start` → `LocalSnaps`/`SnapsToDownload` loop → `Downloaded` → `SeedSnaps` (copy files) → `WriteMeta`.
- For UC20+, the seed tree is: `<unpack>/system-seed/systems/<label>/` containing `model`, `assertions/`, and kernel info. Snaps pool is at `<unpack>/system-seed/snaps/`.
- Snap fetching: by **snap-id** + **channel** from the Store REST API (`/v2/snaps/*`). The Store resolves architecture, finds the correct revision.
- Local snaps via `--snap ./path/to/snap.snap`: the snap is copied into the seed pool. Requires `grade: dangerous` in the model assertion.
- Extra assertions via `--assertion ./file.assert`: any assertion type except `snap-declaration`, `snap-revision`, `model`, `serial`, `validation-set`.

**Stage 7 — populate_bootfs_contents:**
- Uses `gadget.NewMountedFilesystemWriter()` to write content entries from gadget.yaml.
- Content entries with `source`/`target` are resolved relative to the gadget snap root.
- For grub: writes `grubx64.efi` → `EFI/ubuntu/grubx64.efi`, `shim.efi.signed` → `EFI/ubuntu/shimx64.efi` and `EFI/boot/bootx64.efi`.
- For u-boot: writes `boot.scr`, `uEnv.txt`, `boot.sel`.

**Stage 8 — populate_prepare_partitions:**
- Each structure in gadget.yaml becomes a partition (or raw content area).
- Bare structures (no filesystem): raw content is `dd`'d into the image at the specified offset.
- Filesystem structures: `mkfs.vfat` for vfat, `mkfs.ext4` for ext4. Content is populated into the filesystem image, then written to the disk image.

**Stage 9 — make_disk:**
- Uses `go-diskfs` library for disk creation and partitioning.
- GPT partition table generated by `partition.GeneratePartitionTable()`.
- Data written at calculated offsets using raw disk writes.
- Partition sizes: computed from `size`/`min-size` in gadget.yaml, grown by `--image-size` if larger.

### 1.3 CLI Options (Key Ones)

```
ubuntu-image snap [options] model.assertion

  -O, --output-dir DIR      Output directory for .img files
  -w, --workdir DIR         Working directory (preserved if --resume)
  -i, --image-size SIZE     Disk image size (bytes, or M/G suffix)
  -c, --channel CHANNEL     Default snap channel override
  --sector-size SIZE        512 (default) or 4096
  --snap SNAP[=channel]     Extra snap (local path or store name)
  --revision NAME:REV       Pin specific snap revision
  --preseed                 Preseed the image (UC20+)
  --preseed-sign-key NAME   Key to sign preseed assertion
  --assertion FILE          Extra assertions to embed
  --cloud-init USERDATA     Cloud-init user-data file
  --disable-console-conf    Disable console-conf
  --factory-image           Set factory boot hint
  --validation=ignore|enforce  Validation set enforcement
  --allow-snapd-kernel-mismatch  Don't error on snapd/kernel version mismatch
```

### 1.4 Multi-Volume Support

gadget.yaml can define multiple volumes (e.g., `pc` for internal disk + `sdcard` for SD card on ARM). `--image-size` supports per-volume sizing:
```
--image-size 0:2G,sdcard:8G
--image-size sdcard:8G
```
Volumes are 0-indexed by default. eMMC volumes (`schema: emmc`) skip disk image creation — they're written at runtime.

## 2. gadget.yaml Anatomy

The gadget.yaml lives at `meta/gadget.yaml` inside a gadget snap. It defines the disk layout that snapd uses at build time and at runtime (for updates).

### 2.1 Schema

```yaml
volumes:
  <volume-name>:
    schema: gpt | mbr | emmc      # Disk partition scheme (default: gpt)
    bootloader: grub | u-boot | piboot | lk  # Bootloader type
    structure:                      # Ordered list of partitions/regions
      - name: <string>             # Human-readable name
        type: <GUID | bare | mbr>  # GPT type GUID, "bare" for raw, "mbr" for MBR
        role: system-seed | system-boot | system-save | system-data  # snapd roles
        filesystem: ext4 | vfat | none  # Filesystem (omit for bare)
        label: <string>            # Filesystem label (snapd uses specific labels)
        offset: <size>             # Offset from start of disk (e.g., 1M)
        offset-write: <path>:<offset>  # Write offset value at given path in image
        size: <size>               # Partition size (e.g., 750M, 1G)
        min-size: <size>           # Minimum size (for resizing)
        update:
          edition: <int>           # Content edition (increment to force update)
          action: skip |                            # Don't update this structure
                 gadget |                          # Update from gadget snap
                 script |                          # Run update script
                 create |                          # Create new partition
                 grow |                             # Grow to fill space
                 shrink |                           # Shrink to min-size
                 replacement                        # Replace entire structure
        content:                   # Files to place in this partition
          - source: <file>         # File relative to gadget snap root
            target: <path>         # Destination path within filesystem
          - image: <file>          # Raw image to dd (for bare structures)
            offset: <size>         # Offset within the structure
        tier: system | workload    # (UC26+) tier classification
```

### 2.2 Reserved Roles and Labels

snapd recognizes these roles and labels (from `gadget/gadget.go` in snapd):

| Role/Label | GUID | Filesystem | Mount Point | Purpose |
|-----------|------|------------|-------------|---------|
| `system-seed` / `ubuntu-seed` | `C12A7328-F81F-11D2-BA4B-00A0C93EC93B` (ESP) | vfat | `/run/mnt/ubuntu-seed` | Recovery system, model assertion, snap pool |
| `system-boot` / `ubuntu-boot` | `0FC63DAF-8483-4772-8E79-3D69D8477DE4` | ext4 | `/run/mnt/ubuntu-boot` | Run-mode kernel, bootloader config |
| `system-save` / `ubuntu-save` | `0FC63DAF-8483-4772-8E79-3D69D8477DE4` | ext4 | `/run/mnt/ubuntu-save` | Device identity backup, snap persistent data |
| `system-data` / `ubuntu-data` | `0FC63DAF-8483-4772-8E79-3D69D8477DE4` | ext4 | `/var/lib/snapd` (bind) | User data, expanded at install |

**Important:** The same GUID `0FC63DAF-...` is used for system-boot, system-save, and system-data. snapd distinguishes them by **role**, not GUID. The `ubuntu-seed` partition uses the EFI System Partition GUID because UEFI firmware boots from it directly.

### 2.3 Annotated pc-amd64 gadget.yaml (UC24)

Source: `canonical/pc-gadget/24/gadget/gadget-amd64.yaml`

```yaml
volumes:
  pc:
    schema: gpt
    bootloader: grub                # GRUB bootloader (shim → grubx64.efi chain)
    structure:
      - name: mbr
        type: mbr                   # Master Boot Record (440 bytes)
        size: 440
        update:
          edition: 1
        content:
          - image: mbr.img          # Pre-built MBR binary (writes error message)

      - name: BIOS Boot
        type: 21686148-6449-6E6F-744E-656564454649  # BIOS Boot Partition GUID
        size: 1M
        offset: 1M                  # After MBR
        update:
          edition: 2

      - name: ubuntu-seed
        role: system-seed           # snapd: recovery system partition
        filesystem: vfat            # Must be vfat for UEFI ESP
        type: C12A7328-F81F-11D2-BA4B-00A0C93EC93B  # ESP GUID
        size: 1200M                 # ~2× recovery systems for remodeling
        update:
          edition: 3
        content:
          - source: grubx64.efi
            target: EFI/ubuntu/grubx64.efi
          - source: shim.efi.signed
            target: EFI/ubuntu/shimx64.efi
          - source: boot.csv
            target: EFI/ubuntu/bootx64.csv
          - source: fb.efi
            target: EFI/boot/fbx64.efi
          - source: shim.efi.signed
            target: EFI/boot/bootx64.efi  # Fallback boot path

      - name: ubuntu-boot
        role: system-boot           # snapd: run-mode kernel partition
        filesystem: ext4            # ext4 (symlinks to kernel, vfat forbids them)
        type: 0FC63DAF-8483-4772-8E79-3D69D8477DE4
        size: 750M                  # Plenty for kernel + grub assets
        update:
          edition: 1
        content:
          - source: grubx64.efi
            target: EFI/boot/grubx64.efi

      - name: ubuntu-save
        role: system-save           # snapd: device identity backup
        filesystem: ext4
        type: 0FC63DAF-8483-4772-8E79-3D69D8477DE4
        min-size: 16M               # Minimum for encrypted systems
        size: 32M                   # Recommended size

      - name: ubuntu-data
        role: system-data           # snapd: user/system data (expanded at install)
        filesystem: ext4
        type: 0FC63DAF-8483-4772-8E79-3D69D8477DE4
        size: 1G                    # Minimal; expanded by snapd at first boot
```

### 2.4 Gadget Snap Filesystem Layout

A built gadget snap contains (source: pc-gadget repo):

```
snap/
  snapcraft.yaml          # Build definition
  hooks/
    prepare-device        # Runs on first boot; can set MODEL_APIKEY, etc.
    configure             # Snap configure hook
    default-configure     # Default configure hook
gadget/
  gadget-amd64.yaml       # Architecture-specific gadget.yaml
  gadget-arm64.yaml       # ARM64 variant
  legacy-bios/
    mbr.img               # MBR binary for BIOS boot
  shim.efi.signed         # Signed shim bootloader (Secure Boot)
  grubx64.efi             # GRUB EFI binary
  fbx64.efi               # Fallback boot EFI
  boot.csv                # GRUB boot entries
  grub.conf               # Empty file; signals snapd this is a grub gadget
grub/                     # (alternative GRUB setup for non-SecureBoot)
u-boot/                   # (for ARM gadgets)
  boot.scr.in             # U-Boot script template
  uEnv.txt                # U-Boot environment
```

### 2.5 Boot Asset Details

**GRUB (UEFI):**
- `shim.efi.signed` → `EFI/boot/bootx64.efi` (fallback) + `EFI/ubuntu/shimx64.efi`
- `grubx64.efi` → `EFI/ubuntu/grubx64.efi`
- `boot.csv` → `EFI/ubuntu/bootx64.csv` (GRUB menu entries)
- `grub.conf` → empty file at snap root (signals grub bootloader to snapd)
- `grubenv` → created by snapd at build time in `EFI/ubuntu/` (manages boot state)

**U-Boot (ARM):**
- `boot.scr` → compiled from `boot.scr.in` via `mkimage`
- `uEnv.txt` → environment file sourced by U-Boot
- `boot.sel` → NVRAM-style file (`mkenvimage`) for boot selection
- `uboot.conf` → empty file (signals u-boot bootloader to snapd)

## 3. Model Assertion

A model assertion is a signed YAML document describing a device's snap composition. It's both the build recipe (for ubuntu-image) and the device identity (for snapd at runtime).

### 3.1 JSON Input (Before Signing)

```json
{
    "type": "model",
    "series": "16",
    "model": "ubuntu-core-24-amd64",
    "architecture": "amd64",
    "authority-id": "<your-developer-id>",
    "brand-id": "<your-developer-id>",
    "timestamp": "2024-04-19T08:42:32+00:00",
    "base": "core24",
    "grade": "dangerous",
    "snaps": [
        {
            "name": "pc",
            "type": "gadget",
            "default-channel": "24/stable",
            "id": "UqFziVZDHLSyO3TqSWgNBoAdHbLI4dAH"
        },
        {
            "name": "pc-kernel",
            "type": "kernel",
            "default-channel": "24/stable",
            "id": "pYVQrBcKmBa0mZ4CCN7ExT6jH8rY1hza"
        },
        {
            "name": "core24",
            "type": "base",
            "default-channel": "latest/stable",
            "id": "dwTAh7MZZ01zyriOZErqd1JynQLiOGvM"
        },
        {
            "name": "snapd",
            "type": "snapd",
            "default-channel": "latest/stable",
            "id": "PMrrV4ml8uWuEUDBT8dSGnKUYbevVhc4"
        },
        {
            "name": "my-app",
            "type": "app",
            "default-channel": "latest/stable"
        }
    ]
}
```

### 3.2 Required Fields

| Field | Value | Notes |
|-------|-------|-------|
| `type` | `"model"` | Always "model" |
| `series` | `"16"` | Always "16" (even for UC24; the "rolling" series) |
| `model` | `"ubuntu-core-24-amd64"` | Device model identifier |
| `architecture` | `"amd64"` | Debian architecture name |
| `authority-id` | `"<account-id>"` | Must match `brand-id` for custom models |
| `brand-id` | `"<account-id>"` | Your Ubuntu One developer ID |
| `base` | `"core24"` | Base snap name |
| `timestamp` | ISO 8601 UTC | `date -Iseconds --utc` |
| `snaps` | list | See below |

### 3.3 Snaps List

Each entry has:

| Key | Required | Notes |
|-----|----------|-------|
| `name` | yes | Snap name |
| `type` | yes | `gadget`, `kernel`, `base`, `snapd`, or `app` |
| `id` | no* | Store snap-id. **Omit for local snaps** (grade: dangerous only) |
| `default-channel` | no | Default: `"latest/stable"` |
| `presence` | no | `"required"` (default) or `"optional"` |
| `modes` | no | Recovery modes: `["run"]`, `["run", "ephemeral"]`, etc. |
| `components` | no | Map of component name → presence/modes |

*`id` is mandatory for `grade: signed`/`secured` models.

### 3.4 Grade

| Grade | Behavior |
|-------|----------|
| `dangerous` | Allows local snaps (no snap-id), devmode, extra snaps. **Use for dev.** |
| `signed` | No unsigned snaps. All snaps must have store snap-ids. **Default.** |
| `secured` | Like signed + mandatory FDE + secure boot. |

**Critical:** `--snap` (adding extra snaps) requires `grade: dangerous`. With `grade: signed`, extra snaps must be declared with `"presence": "optional"` in the model and added via `--snap`.

### 3.5 Signing Workflow

```bash
# 1. Create a GPG key (one-time)
snapcraft create-key "my-brand"

# 2. Register the key with your Ubuntu One account
snapcraft register-key "my-brand"

# 3. Sign the model assertion
# Update timestamp first, then:
snap sign -k "my-brand" model.json > model.assertion

# The signed output includes:
#   sign-key-sha3-384: <key-fingerprint>
#   body: <base64-encoded-signature>
```

### 3.6 Validation Sets (Optional)

```json
"validation-sets": [
    {
        "account-id": "<account-id>",
        "name": "my-validated-set",
        "sequence": 3,
        "mode": "enforce"
    }
]
```

- `enforce`: device must always have this set installed.
- `prefer-enforce`: initially enforced, can be forgotten later.
- Without `sequence`: latest sequence is fetched at build time.

### 3.7 Components (UC24+)

```json
{
    "name": "pc-kernel",
    "type": "kernel",
    "default-channel": "26.04/beta",
    "id": "pYVQrBcKmBa0mZ4CCN7ExT6jH8rY1hza",
    "components": {
        "nvidia-590-uda-ko": {
            "presence": "optional",
            "modes": ["run"]
        },
        "nvidia-590-uda-user": "optional"
    }
}
```

Components are optional parts of a snap. In the model, they're declared per-snap with `presence` (required/optional) and optionally `modes`.

## 4. Store Interaction

### 4.1 How ubuntu-image Fetches Snaps

1. **Model assertion resolution:** ubuntu-image passes the model to `snapd/image.Prepare()`, which creates a `seedwriter.Writer`.
2. **Seed writer flow:**
   - Parses model assertion to get snap list (name, type, snap-id, channel).
   - For each snap with a `snap-id`: queries Store API (`/v2/snaps/<snap-id>/info`) to get current revision for the channel+architecture.
   - Downloads snap files to `seed/snaps/` pool.
   - Fetches snap declarations, snap revisions, and account-key assertions.
3. **Channel semantics:** `"<track>/<risk>"` or `"<track>/<risk>/<branch>"`.
   - Track: release cycle (e.g., `24`, `26.04`). Default: `latest`.
   - Risk: `stable`, `candidate`, `beta`, `edge`.
   - Branch: named delta (e.g., `fix-bug-123`). Optional.
4. **Architecture filtering:** Store returns only snaps matching the model's `architecture`.

### 4.2 Local Snaps (--snap flag)

```bash
ubuntu-image snap model.assertion --snap ./my-custom-gadget.snap
ubuntu-image snap model.assertion --snap my-app=stable
ubuntu-image snap model.assertion --snap ./local-app.snap=stable  # local + channel
```

- `--snap ./path.snap`: local snap file, copied into seed pool.
- `--snap name=channel`: store snap, fetched from that channel.
- `--snap name`: store snap, default channel.
- **Requires `grade: dangerous`** for local snaps (no snap-id verification).
- Multiple `--snap` flags supported.

### 4.3 Revision Pinning

```bash
ubuntu-image snap model.assertion --revision pc-kernel:2421
```

Pins a specific revision. Updates still come from the specified (or default) channel.

### 4.4 Fully Offline Builds

**There is no `--offline` flag.** To build offline:

1. Pre-download all snaps as `.snap` files.
2. Use `grade: dangerous` in model assertion.
3. Pass each snap via `--snap ./path/to/snap.snap`.
4. Do **not** include snap-ids in the model (or omit them for dangerous grade).
5. Store assertions (snap-declaration, snap-revision) must be pre-cached in `~/.local/share/snapd/assertions/` or provided via `--assertion`.

**Alternative (partial offline):** Snap Store proxy. Point the device at a local proxy that caches Store responses.

### 4.5 Store REST API (Reference)

Key endpoints used by snapd internally:
- `GET /v2/snaps/<snap-id>/info` — snap metadata (name, channels, revisions)
- `GET /v2/snaps/<snap-id>/rev/<rev>` — specific revision info
- `GET /v2/assertions/<type>/<key>` — assertion chain
- `POST /v2/snaps/<snap-id>/download` — snap file download

## 5. Gadget Snap Internals

### 5.1 What a Gadget Snap Contains

A gadget snap is a standard snap (`type: gadget`) containing:

1. **`meta/gadget.yaml`** — The partition layout definition.
2. **Bootloader binaries** — grubx64.efi, shim.efi.signed, or u-boot binaries.
3. **Boot configuration** — boot.csv, grub.conf, uEnv.txt, boot.sel.
4. **`snap/hooks/prepare-device`** — Hook run on first boot (sets API keys, configures device).
5. **`snapcraft.yaml`** — Build definition for the gadget snap itself.

### 5.2 snapcraft.yaml for Gadget

```yaml
name: pc
version: '24-0.2'
type: gadget                    # MUST be "gadget"
base: core24                    # Must match model's base
summary: PC gadget for generic devices
confinement: strict
grade: stable

assumes:
  - snapd2.63                   # Minimum snapd version

parts:
  boot-assets:
    plugin: nil
    build-packages: [sbsigntool]
    stage-packages:
      - grub-efi-${CRAFT_ARCH_BUILD_FOR}-signed
      - shim-signed
    override-build: |
      # Extract and verify signed bootloaders
      # Install shim.efi.signed, grubx64.efi, fb.efi, boot.csv
      # Create grub.conf (empty file)

  gadget:
    plugin: nil
    source: gadget
    override-build: |
      # Copy architecture-specific gadget.yaml to gadget.yaml
      install -m 644 gadget-${CRAFT_ARCH_BUILD_FOR}.yaml \
        ${CRAFT_PROJECT_DIR}/gadget.yaml

hooks:
  prepare-device:
    environment:
      MODEL_APIKEY: ""
```

### 5.3 build-base vs base

- `base`: runtime base snap (e.g., `core24`). Must match model.
- `build-base`: build environment (only for devel releases). Omit for stable.
- `grade: stable` for production gadgets; `grade: devel` for development.

### 5.4 The prepare-device Hook

Runs during first boot (install mode). Can:
- Set `MODEL_APIKEY` for serial vault communication.
- Configure device-specific network settings.
- Call `snapctl system-mode` to detect mode (install/run/recover).
- Call `snapctl reboot --halt` to pause before run mode.

### 5.5 Gadget/Base Version Compatibility

- The gadget snap's `base` field must match the model's `base` (e.g., `core24`).
- The gadget snap is cross-checked against the base snap at build time.
- Mismatch → ubuntu-image error: "gadget snap ... is not compatible with base snap".

## 6. Extras

### 6.1 Adding Extra Snaps

**Via model assertion (preferred for production):**
```json
{
    "name": "my-app",
    "type": "app",
    "default-channel": "latest/stable",
    "presence": "optional"
}
```
Then: `ubuntu-image snap model.assertion --snap my-app`

**Via command line (development only):**
```bash
ubuntu-image snap model.assertion --snap ./my-app.snap --snap another-app=edge
```

### 6.2 Preseeding (UC20+)

Preseeding pre-configures the image so first boot is faster:

```bash
ubuntu-image snap model.assertion --preseed
```

- Requires `--preseed-sign-key` (or uses default key).
- Creates preseed assertions in the image.
- Enables `--sysfs-overlay` for custom sysfs configuration.
- Preseeding runs snapd in a chroot to pre-configure the system.

### 6.3 arm64 Builds

For Raspberry Pi:
```bash
# Use pi-gadget instead of pc-gadget
# Model assertion:
{
    "model": "ubuntu-core-24-pi-arm64",
    "architecture": "arm64",
    "base": "core24",
    "snaps": [
        {"name": "pi", "type": "gadget", "default-channel": "24/stable", "id": "..."},
        {"name": "pi-kernel", "type": "kernel", "default-channel": "24/stable", "id": "..."},
        {"name": "core24", "type": "base", "default-channel": "latest/stable", "id": "..."},
        {"name": "snapd", "type": "snapd", "default-channel": "latest/stable", "id": "..."}
    ]
}

# Build:
ubuntu-image snap my-pi-model.assertion --allow-snapd-kernel-mismatch
```

### 6.4 Cloud-init Integration

```bash
ubuntu-image snap model.assertion --cloud-init user-data.yaml
```

The user-data file is copied to the image for cloud-init processing on first boot.

### 6.5 Factory Image

```bash
ubuntu-image snap model.assertion --factory-image
```

Sets a boot flag that can be checked by `snapctl system-mode` in the prepare-device hook. Cleared before run mode.

### 6.6 UC26 Changes (if available by Aug 2026)

Based on Canonical announcements:
- **Chisel-based build:** Replaces some debootstrap-based rootfs assembly.
- **Components GA:** First-class component support in model assertions.
- **Reduced update sizes:** Delta-based snap updates.
- **Livepatch:** Kernel livepatching in base snap.
- **Python removed from core base:** Minimal base snap.
- **OpenAPI-compliant snapd REST API.**

### 6.7 Disk Encryption

Model assertion `storage-safety` field:
- `prefer-unencrypted`: no encryption (default)
- `prefer-encrypted`: encrypt if hardware supports
- `encrypted`: mandatory encryption (fails without hardware support)

Requires `ubuntu-save` partition (32MB recommended) and `grade: secured`.

## 8. Gotchas for Implementers

1. **`--snap` requires `grade: dangerous`** — Non-negotiable. With `grade: signed`, you can only add snaps that have `"presence": "optional"` in the model and use `--snap name` (store snaps only).

2. **Local snaps need store assertions** — Even with `grade: dangerous`, snapd validates assertions. If building fully offline, you need pre-cached `snap-declaration` and `snap-revision` assertions.

3. **gadget.yaml lives at `meta/gadget.yaml`** inside the snap, not at the root. The `gadget` part in snapcraft.yaml must install it there.

4. **UEPI ESP must be vfat** — The `ubuntu-seed` partition with role `system-seed` and ESP GUID must be vfat. UEFI firmware won't boot ext4.

5. **system-boot must be ext4** — snapd creates symlinks to kernel files on this partition; symlinks are impossible on vfat.

6. **Same GUID for 3 partitions** — `system-boot`, `system-save`, and `system-data` all use `0FC63DAF-8483-4772-8E79-3D69D8477DE4`. snapd identifies them by **role**, not GUID. Don't try to use GUIDs alone.

7. **`--image-size` is a hint, not a guarantee** — If smaller than minimum calculated size, it's ignored with a warning. The rootfs size is computed from actual content + ext4 overhead.

8. **Sector size matters** — Default 512. Use `--sector-size 4096` for 4Kn drives. All sizes are aligned to sector boundaries.

9. **Multi-volume naming** — When gadget.yaml has multiple volumes, `--image-size` needs the volume name or index: `--image-size sdcard:8G`.

10. **Model assertion timestamp must be fresh** — Old timestamps may cause issues with assertion validation. Use `date -Iseconds --utc`.

11. **snapd writes grubenv at build time** — Don't pre-populate it. snapd creates `EFI/ubuntu/grubenv` during image assembly.

12. **`prepare-device` hook is runtime** — It runs on the device, not during build. Environment variables in `hooks.prepare-device.environment` are embedded in the snap but only available at runtime.

13. **Seed partition size for remodeling** — Must be ~2× the size of one recovery system to hold two systems simultaneously (for A/B recovery).

14. **Architecture must match** — The model's `architecture` field filters Store results. Building an arm64 image from an amd64 host works (cross-build), but the model assertion must declare `arm64`.

15. **ubuntu-image requires root** — The tool doesn't check; it fails silently or with cryptic errors if not root. Always `sudo`.
