01 Payload bay

Mission Cassini — payloads

Everything below lives flat in one directory on the download lane, download.nau.rclb.dev/missions/cassini/ — one whole-disk mission image for x86_64 UEFI (the release names the arch amd64), its signed manifest, and the checksum manifest with its detached signature. Filenames follow nau-<mission>-<version>-<arch> exactly as the release flow emits them.

Whole-disk GPT artifact: ESP with a UKI, two verity-protected root slots, hash partitions, and the state partition that grows on first boot. Install is a copy of these bytes — nothing re-lays-out partitions at flash time.

02 Verification walkthrough

From download to proven write

Six flight steps, in order, copy-pasteable. Trust is established on the machine that flashes — a flashed device cannot verify its own medium, and the release key never travels on the download lane it signs.

  1. Pull the media set

    Four files: the image, the signed manifest, the checksum manifest, and the signature over it. Caddy serves the tree with native Range support, so a broken transfer resumes — re-run the same pull with -C - and it continues where it stopped. The image is multi-gigabyte; the other three are small.

    base=https://download.nau.rclb.dev/missions/cassini
curl -fLO $base/nau-cassini-1.0.0-amd64.img
curl -fLO $base/nau-cassini-1.0.0-amd64.manifest.json
curl -fLO $base/SHA256SUMS
curl -fLO $base/SHA256SUMS.gpg

  2. Establish the release key — out of band

    The signature is made by the ceremony key's sysupdate identity — an OpenPGP Ed25519 key whose public half is baked into every Nau rootfs at /usr/lib/systemd/import-pubring.pgp, covered by the dm-verity the device boots. Import that public key into your keyring from a channel you already trust: the brand's key-distribution channel, a keychain you received in person, a Nau machine you own. Never fetch the key from the download lane itself — a lane that serves both the bytes and the key that blesses them verifies nothing (ADR-0033 D7).

    gpg --import nau-release-key.asc   # from a trusted channel, never from the lane
gpg --list-keys --with-subkeys       # confirm the fingerprint out of band

  3. Verify the checksum manifest signature

    The checksum proves the bytes arrived intact; this signature proves they were released. One command over the two small files:

    gpg --verify SHA256SUMS.gpg SHA256SUMS
# gpg: Good signature from "…" [unknown]

    Flight rule: anything that is not a good signature from the expected key means do not flash. Stop the countdown and keep the payload on the ground.

  4. Check the bytes

    Now the hashes — --ignore-missing because you fetched the media set, not the sysupdate payloads the same sums also cover:

    sha256sum --check --ignore-missing SHA256SUMS
# nau-cassini-1.0.0-amd64.img: OK
# nau-cassini-1.0.0-amd64.manifest.json: OK

  5. Flash by-id, never by raw sdX

    The kernel letter can change between boots; the by-id name carries the model and serial. Confirm what the name resolves to before anything touches the disk — a destructive step is documented, never silent.

    ls -l /dev/disk/by-id/   # confirm model + serial

sudo dd if=nau-cassini-1.0.0-amd64.img \
        of=/dev/disk/by-id/<model>_<serial> \
        bs=4M status=progress conv=fsync
sync

  6. Prove the write, then boot

    verify-image is read-only and unprivileged. It refuses a mounted, undersized, or foreign-signature target without an explicit override — which is exactly the argument for running it. It re-checks the device's roothash and the manifest's Ed25519 signature against the ceremony keychain (~/.config/nau/keys/*.pub), so no --key is needed once that is installed; a --key copy, like the key in step 2, comes out of band or nowhere. Record the reported verified_key_id with the release notes, then pull the medium and boot.

    nau verify-image \
    --device /dev/disk/by-id/<model>_<serial> \
    --manifest nau-cassini-1.0.0-amd64.manifest.json

    Slot A runs Cassini; the update_source baked into the image points at this same tree, so sysupdate A/B transfers arrive over the lane you flashed from — and every update re-runs this whole verification on the device: gpg against the embedded keyring, then the SHA256SUMS hash checks. When a mission update lands you switch slots, and rollback is the other slot, still there.

03 Layout contract

The tree every link assumes

The download lane is append-only for released missions: a published image is an artifact, never a cache entry. The media set is flat — no subdirectories — because installed machines resolve every name relative to the baked update_source URL. This shape is the whole contract; filenames included.

missions/cassini/
├── current.json                       update pointer — publish-maintained (plan decision 4)
├── SHA256SUMS                         checksum manifest — one line per file below
├── SHA256SUMS.gpg                     detached OpenPGP signature over SHA256SUMS
├── nau-cassini-1.0.0-amd64.img          whole-disk mission image
├── nau-cassini-1.0.0-amd64.manifest.json signed image manifest (Ed25519)
├── root_1.0.0_<partuuid>.img             sysupdate payload — rootfs extent
├── verity-hash_1.0.0_<partuuid>.img     sysupdate payload — verity hash extent
└── <name>_1.0.0.efi                     sysupdate payload — the staged UKI
  • nau-cassini-1.0.0-amd64 — the media stem, built from the signed manifest's own version and arch fields (nau-<mission>-<version>-<arch>). The image and its manifest are siblings; verification needs both.
  • SHA256SUMS + SHA256SUMS.gpg — siblings at the mission root, the pair systemd-sysupdate Verify=yes fetches on the device. The build's own contract test signs the sums, then refuses any sysupdate drop-in whose source names miss the signed list — a rename on either side fails the build, not your update night.
  • root_… / verity-hash_… / …_.efi — the A/B transfer payloads installed machines pull. <partuuid> is the roothash-derived GUID the build pinned on its slots (the @u a transfer pattern expands at update time); the version is its @v. You don't need them to install — flashing the whole disk is the install path.
  • current.json — the one moving part, rewritten by publish at each release so version and directory reshuffles never require a re-image. Installed machines follow it; the flash walkthrough above doesn't need it.
