02 Verification walkthrough

From pointer to proven write

Six flight steps, in order. Trust is established at download, not on the device — a flashed machine cannot verify its own medium.

  1. Read the mission pointer

    current.json is the ground truth for what Cassini is today. Installed machines read the same file, so your install and their updates always agree.

    curl -fsS https://download.nau.rclb.dev/missions/cassini/current.json

  2. Pull the image and its checksums

    Caddy serves the tree with native Range support, so a broken transfer resumes — re-run the same pull with -C - and it continues where it stopped.

    curl -fLO https://download.nau.rclb.dev/missions/cassini/images/nau-cassini-1.0-x86_64.img
curl -fLO https://download.nau.rclb.dev/missions/cassini/SHA256SUMS

sha256sum --check --ignore-missing SHA256SUMS
# nau-cassini-1.0-x86_64.img: OK

  3. Verify the signed image manifest

    Fetch the manifest entry the tree advertises for the image and verify its signature against the release key. The checksum proves the bytes arrived intact; the manifest signature proves they were released. Confirm the key fingerprint out of band. Custody is one trusted machine under the update-signing key ceremony (ADR-0024).

    Flight rule: a failed signature means do not flash. Stop the countdown and keep the payload on the ground.

  4. Flash by-id, never by raw sdX

    The kernel letter can change between boots; the by-id name carries the model and serial. Confirm what the name resolves to before anything touches the disk — a destructive step is documented, never silent.

    ls -l /dev/disk/by-id/   # confirm model + serial

sudo dd if=nau-cassini-1.0-x86_64.img \
        of=/dev/disk/by-id/<model>_<serial> \
        bs=4M status=progress conv=fsync

  5. Prove the write

    verify-image is read-only and unprivileged. It refuses a mounted, undersized, or foreign-signature target without an explicit override — which is exactly the argument for running it.

    shuttle verify-image --device /dev/disk/by-id/<model>_<serial>

  6. Boot and ride the ground track

    Pull the medium, boot the ship. Slot A runs Cassini; the update_source baked into the image points at this same tree, so sysupdate A/B transfers arrive over the lane you flashed from. When a mission update lands, you switch slots — and rollback is the other slot, still there.

03 Layout contract

The tree every link assumes

The download lane is append-only for released missions: a published image is an artifact, never a cache entry. This shape is the whole contract — filenames included.

missions/cassini/
├── current.json            mission pointer — the only moving part
├── SHA256SUMS              checksum manifest, one line per artifact
├── images/
│   └── nau-cassini-1.0-x86_64.img   whole-disk mission image
├── manifest/               signed image manifest (ADR-0044 D5)
└── updates/                sysupdate transfer artifacts
  • current.json — updated by the publish wrapper at each release. The update_source URL baked into every image points at the directory, so the pointer can move without a re-image.
  • images/nau-cassini-1.0-x86_64.img — the only image filename that exists for Cassini 1.0. Names follow nau-<mission>-<version>-<arch>.img; nothing else appears in images/.
  • SHA256SUMS — lives beside the pointer at the mission root, checked with --ignore-missing so extra local files don't disturb the pass.
  • manifest/ and updates/ — the signature proof of step 3 and the transfer payloads installed machines pull. Both are part of the same mission tree, same certificate, same lane.
